## 판정부터 고정한다

이 실행은 세 가게 중 무엇이 인터넷에 “존재하는지” 판정하지 않는다. 고정된 질의와 열람 범위에서 어떤 기록이 회수되는지를 시험한다. 따라서 결과가 없을 때 허용되는 문장은 `not_found_under_protocol`뿐이다.

또한 다음 결과를 분리한다.

- `retrieval_hit`: 검색 결과 범위 안에서 bay별 식별자와 장소 연결이 회수됨.
- `entity_location_match`: 후보 사업체 또는 간판이 대상 장소와 충분한 단서로 연결됨.
- `contemporaneous_2015_anchor`: 2014-01-01~2016-12-31에 생성된 자료가 후보와 대상 장소를 연결함.
- `retrospective_2015_anchor`: 나중 자료가 후보의 2015년 대상 장소 존재를 명시적으로 연결함.
- 현재 지점 정보만 회수된 경우: 장소 연결에는 쓸 수 있지만 2015년 기록 회수로 승격하지 않음.

제공된 2015년 Google 거리영상은 표본 구성과 정답 간판 확인에만 사용한다. 세 bay 모두에서 검색 성공으로 세지 않는다.

## 실행 설계

단일 조사자가 K0 → K1 → K2를 순차 실행한다. 그러므로 이는 `progressive retrieval ladder`이지 지식 조건 간 독립 비교가 아니다. 먼저 Google 웹 검색을 실행한 뒤 Naver 웹 검색의 사전 지정 질의를 반복한다. Naver 실행 역시 Google 결과를 이미 본 조사자의 교차플랫폼 반복이며, 블라인드 재현이나 플랫폼 효과 추정으로 해석하지 않는다.

실행 순서는 기계 판독 파일 [`dry-run-query-plan.v0.1.json`](dry-run-query-plan.v0.1.json)의 `queries[].order`와 정확히 같다. 질의 문자열을 교정하거나 별칭을 추가하지 않는다.

### 검색면

| 코드 | 역할 | 고정 URL 조건 | 통제되지 않는 것 |
|---|---|---|---|
| `GOOGLE_WEB` | 1차 lane | `hl=ko`, `pws=0` 요청 | 위치, 계정 상태, 실험군, 색인 시점 |
| `NAVER_WEB` | 사후 교차플랫폼 반복 | 표준 통합검색 query URL | 위치, 계정 상태, 실험군, 색인 시점 |

각 실행에서 실제 로그인 표시 여부, 시각, 표시된 질의, 리디렉션, 차단 여부를 기록한다. `pws=0`은 개인화 제거를 보증한다고 해석하지 않는다.

### 열람 범위

- 질의별 자연검색 결과 상위 10개까지만 기록한다.
- 광고는 제외한다.
- 지도·블로그·이미지·AI 요약 같은 모듈은 자연검색 순위와 분리해 기록한다.
- 2페이지로 넘어가지 않는다.
- 후보 원문 클릭은 질의별 최대 2개다.
- 전화번호를 질의에 사용하지 않는다.
- CAPTCHA 또는 자동화 차단이 나타나면 우회하지 않고 `blocked`로 끝낸다.
- 검색 중 새 별칭이나 법적 명칭을 알게 되어도 사전 지정 질의에 추가하지 않는다. 그것은 K3 노출로만 기록한다.

## 지식 조건

- K0: 주소·건물/상가명·2015년만 사용한다. bay 간판과 업종은 쓰지 않는다.
- K1: bay별 일반 업종 또는 불완전한 기억 단서를 추가한다. 정규화된 정답 상호는 쓰지 않는다.
- K2: 2015년 영상에서 읽힌 정확한 간판 문자열을 쓴다. 이 단계는 일반 발견 능력이 아니라 oracle-aided verification이다.

K0는 세 bay에 공유되는 장소 검색이다. K1과 K2는 bay별로 기록한다. 앞선 결과에서 다른 bay의 정답이 노출되면 `cross_bay_answer_exposure`로 남기되 질의를 고치지 않는다.

## 시간 예산

| 셀 | 벽시계 상한 |
|---|---:|
| K0, 장소 공유 | 5분 |
| K1, bay별 | 5분 |
| K2, bay별 | 10분 |

각 셀의 첫 usable 결과 화면이 보인 때부터 벽시계를 잰다. 네트워크/도구 대기시간은 별도로 남기지만, 이를 이유로 정해진 질의를 몰래 늘리지 않는다. 실행하지 못한 질의는 삭제하지 않고 `budget_exhausted`로 기록한다.

## 유효 증거와 동일성

정확한 상호 하나, 주소 하나, 업종 하나만으로 동일 사업체를 확정하지 않는다. 특히 `야채나라`와 `롤리팝`은 동명이 많을 수 있다. 최소한 bay별 식별자와 장소 단서의 결합 또는 서로 순환하지 않는 두 식별 단서가 필요하다.

검색 스니펫은 “검색면에서 회수 가능했다”는 증거가 될 수 있지만, 원문이 주장하는 모든 사실의 증거는 아니다. 원문을 열지 못했으면 그 한계를 그대로 기록한다. 서로 다른 검색 결과가 같은 원자료를 복제했으면 하나의 `independence_group`으로 묶는다.

## 결과 보존

각 질의에 대해 다음을 남긴다.

- query ID, 정확한 질의, 플랫폼, K 조건, bay ID
- 시작·종료 시각, 결과 페이지 상태, 계정/위치 표시 상태
- 상위 결과의 순위 또는 모듈, 제목, URL, 표시된 날짜, 스니펫
- 채택·기각·모호 판정과 이유
- 클릭한 원문과 확인한 단서
- cross-bay/K3 노출
- 질의 수준의 `observed`, `not_found_under_protocol`, `blocked`, `budget_exhausted`

## 금지되는 해석

- 세 bay의 결과 빈도로 동네 전체나 소상공인 전체의 잔존율을 추정하지 않는다.
- 프랜차이즈와 독립점포의 차이를 인과효과로 부르지 않는다.
- 현재 검색 순위를 2015년 당시의 온라인 가시성으로 소급하지 않는다.
- 행정자료 결과를 일반 웹 기록 생존과 합산하지 않는다.
- Google과 Naver 결과 차이를 플랫폼 효과로 추정하지 않는다. 실행 순서, 로그인, 위치, 색인과 UI가 통제되지 않았다.

## 봉인 절차

검색 결과를 열기 전에 이 문서와 JSON 계획, 기존 프로토콜, scope freeze manifest, bay register의 SHA-256을 별도 manifest에 기록한다. 봉인 후 계획을 고치면 같은 실행 ID를 유지하지 않고 새 계획 버전으로 시작한다.
